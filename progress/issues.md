## #1 conv3x3 结果异常：真正根因是 CFU_OP 宏变量遮蔽

- **状态**：已解决
- **发现日期**：2026-10-06
- **根因定位与修复验证**：2026-10-31
- **问题性质**：软件 Bug，具体为 C 宏作用域中的变量遮蔽
- **硬件结论**：`proc.v` 和 custom-0 数据通路无需因此修改

### 1. 初始现象

conv3x3 CFU 版对拍仅 5/36 通过，错误表现为“行冻结”：

- 第 0 行全部正确；
- 其余各行的结果精确等于第 0 行对应列；
- T1／T2 探针在循环内调用 `CFU_MUL(img[r*8], kern[0])` 时结果错误；
- 加入 3 个 nop 后结果暂时恢复正确。

当时将其诊断为“custom-0 指令 load-use 硬件冒险”，即认为 lw 数据经同步 RAM 晚一拍返回，紧随其后的 custom-0 指令读取了旧值。

**后续实验证明，该诊断错误。**

### 2. 误诊期间的历史处置

- 使用预加载＋展开结构，并在 CFU_OP 宏前加入 3 个 nop。
- 2026-10-31 进行 nop 开销实验：在 preload＋unroll 结构下，去除 nop 后三档优化均 36/36 通过。
- 历史测得 nop 开销恒为 756 cycle/call；1080 条指令中约 30% 被流水线停顿吸收。
- 当时曾据此认为“软件保险冗余，但硬件缺口仍存在，需要修改 proc.v”。该结论的前提同样错误。

preload＋unroll 之所以消除异常，是因为 CFU 操作数不再包含与宏内临时变量同名的 `r`，与指令间隔无关。

### 3. 真正根因

旧版 CFU_OP 宏是 GCC 语句表达式，内部声明了局部变量：

```c
int r;
```

当调用点写成：

```c
CFU_MUL(img[r*8], kern[0])
```

且外层循环变量也叫 `r` 时，宏内的 `int r` 会遮蔽外层循环变量。宏展开后，`img[r*8]` 中的 `r` 绑定到宏内未初始化的临时变量，而不是循环计数器。

### 4. 波形与反汇编证据

VCD 波形和反汇编提供了以下证据：

- 失败迭代的 CFU src1 为 0 或陈旧值；
- load 地址在正确的 `0x100005ac` 与异常地址 `0x1004ffac` 之间变化；
- 异常地址相当于数组基址加上由上一轮乘积计算的偏移，即上一轮 CFU 结果被错误地当作索引参与地址计算；
- 循环反汇编（PC 0x138～0x154）中不存在对相关寄存器的逐轮初始化。

这些现象与宏变量遮蔽一致，不支持原先的硬件 load-use 冒险判断。

### 5. 为什么加入 nop 会暂时恢复正确

加入 3 个 nop 会改变编译后的寄存器分配和指令排布，使相关寄存器中的值偶然不再触发错误。

nop 没有修复任何硬件逻辑，只是掩盖了软件 Bug。因此，“加入 nop 后正确”不能作为硬件存在缺陷的证据。

### 6. 为什么其他实验没有触发

dot256 等正式实验中的 CFU 操作数主要是局部变量、字面量或名为 `i` 的索引，没有与旧宏内部 `r` 同名的变量，因此不会触发该遮蔽问题。

T3／T4 先将操作数取出到临时变量，再调用宏，也天然规避了问题。P1～P5、L2／L3 等不含 `r` 表达式的探针全部通过，与最终根因一致。

### 7. 修复方法

将宏内临时变量改为高区分度名称，并去除内置 nop：

```c
#define CFU_OP(f3, a, b) ({ \
    int _cfu_ret; \
    asm volatile(".insn r 0x0B, " #f3 ", 0, %0, %1, %2" \
        : "=r" (_cfu_ret) : "r" (a), "r" (b)); \
    _cfu_ret; \
})
```

修复后，L1 探针在零指令间隔下输出全部正确：

```text
L1 = L3 = 10192 5096 0 -5096 -10192 7553
```

由此排除了 proc.v 和 custom-0 数据通路存在相应硬件缺陷的可能。

### 8. 经验教训

1. GCC 的 `"=r"` 输出约束会使编译器认为变量已被写入，可能不再给出未初始化诊断，不能依赖编译器发现此类宏遮蔽问题。
2. 宏内临时变量应使用高区分度名称，并避免与调用点变量同名。
3. “加 nop 后正确”不等于“硬件存在 Bug”，应先隔离软件因素，再判断硬件问题。
4. 波形分析应更早纳入排查流程。本次纯软件侧排查耗时较长，而 VCD 波形为最终定位提供了直接证据。

## #2 -O0 下内联汇编编译失败

- **状态**：已解决
- **现象**：编译时报错 `impossible constraint in 'asm'`
- **根因**：funct3 使用 `"i"` 立即数约束，依赖编译器内联和常量传播；-O0 下相关函数不内联，导致约束无法满足
- **修复**：将 CFU_OP 改为宏，并通过 `#f3` 字符串化把 funct3 直接拼入指令文本
- **验证**：修复后可在 -O0／-Os／-O2 三档优化下编译和运行

## #3 程序映像固化导致修改后仿真结果不变

- **状态**：已知悉，通过构建流程规避
- **现象**：修改 `main.c` 后执行 `make run`，输出结果仍与修改前相同
- **根因**：程序经 initf 生成 `memi.txt`／`memd.txt` 后被编入仿真器；单独执行 `make run` 不会触发程序重编译
- **补充现象**：2026-10-31 曾复现执行 make 后 Verilator 仍判断“无变化”并跳过重建，子 make 输出 `Nothing to be done`

### 强制规避规则

修改 `main.c`、相关软件源码或编译优化等级后，必须删除旧仿真器并完整重建：

```bash
rm -rf obj_dir && make OPT=-O0 && make run
rm -rf obj_dir && make OPT=-Os && make run
rm -rf obj_dir && make OPT=-O2 && make run
```

不得仅执行 `make run` 后将旧结果当作新程序的实验数据。

## #5 CFU 乘加组合路径构成当前时序瓶颈

- **状态**：待优化
- **性质**：性能与时序问题，不是功能正确性问题

### 当前证据

160 MHz 和 80 MHz 两次实现的最差路径均通向 CFU 累加寄存器。

160 MHz 最差路径：

```text
cpu/ExMa_rslt_reg[3] → cpu/cfu/acc_reg[25]
```

- 数据路径延迟：11.249 ns
- 逻辑级数：9
- 包含 2 个 DSP48E1、4 个 CARRY4 和若干 LUT

80 MHz 最差路径：

```text
cpu/IdEx_rs1_fwd_Ma_to_Ex_reg_replica → cpu/cfu/acc_reg[28]
```

- 数据路径延迟：12.420 ns
- 逻辑级数：11
- 包含 2 个 DSP48E1、5 个 CARRY4 和若干 LUT

### 当前结论

乘法、累加及相关组合逻辑集中在同一时钟周期内，是当前时序优化的重要对象。80 MHz 虽然通过，但 WNS 仅为＋0.045 ns，时序余量较小。

### 下一步

- 在保持原始设计报告不变的前提下设计优化方案；
- 评估乘法与累加拆分、寄存器插入或 MAC 流水线化；
- 优化后重新进行功能对拍、cycle 测量、资源统计和时序分析；
- 比较优化前后的性能、资源和 Fmax，避免只改善其中一项而忽略其他代价。

## #6 Vivado 报告存在 XDC 与 I/O 约束警告

- **状态**：待审查

### 已观察到的警告

- 若干部件加入 pblock 时得到空 cell 列表；
- `clk_i` 时钟约束存在重复定义和覆盖；
- `rxd_i`、`txd_o` 等信号没有匹配端口，后续属性设置得到空对象；
- `check_timing` 报告 4 个输出端口未设置 output delay；
- 报告方法论中仍有 `XDCC-1` 和 `XDCC-7` 警告。

### 当前已知情况

- 两次时钟汇总均正确显示板载输入时钟为 100 MHz；
- 两次 Clock Wizard 输出分别正确显示为 160 MHz 和 80 MHz；
- 内部寄存器无 no_clock、multiple_clock 等报告问题；
- 上述结果支持当前内部时钟时序分析，但不等于所有板级 I/O 约束都已经完整验证。

### 下一步

- 对照 `main.v` 的实际端口和 `constr/nexys_a7.xdc` 逐项检查；
- 确认空 pblock、无匹配 UART 端口是否由上游板卡裁剪造成；
- 检查重复时钟定义的来源和最终生效约束；
- 确认 4 个输出端口的具体名称及其是否需要 output delay；
- 在结论明确前，不将相关警告写成“无害警告”。

## #7 当前资源数据无法区分 CPU 与 CFU 的独立开销

| 160 MHz | 1804 | 918 | 7 | 19 |
| 80 MHz | 1746 | 884 | 7 | 19 |

这些数据均来自整个 `main` 顶层，包含：

- RV32IM CPU；
- CFU；
- 指令和数据存储器；
- Clock Wizard；
- 外部接口及相关控制逻辑。

两次频率目标下 LUT 和 FF 数量略有变化，而 DSP 和 BRAM 不变，可能与不同目标下的优化、复制和布局布线策略有关。
