# 问题记录

## #1 "custom-0 load-use 硬件冒险"误诊案 —— 真正问题是 CFU_OP 宏变量遮蔽

- **状态**：已解决（2026-10-31 定位根因并修复验证）
- **性质**：软件 bug（C 宏作用域），硬件无缺陷。proc.v 不需要任何修改
- **发现日期**：2026-10-06

### 症状（2026 年 10 月初次发现）
conv3x3 CFU 版对拍 5/36，错误呈"行冻结"——第 0 行全对，其余每行
结果精确等于第 0 行对应列；T1/T2 探针（循环内 `CFU_MUL(img[r*8], kern[0])`）
结果错误，加 3 个 nop 后正确。当时诊断为"custom-0 指令 load-use
硬件冒险"（lw 数据经同步 RAM 晚一拍返回，custom-0 紧跟 lw 读到旧值）。
**该诊断是错误的。**

### 误诊期间的处置（历史记录）
- 规避方案：预加载+展开结构 + CFU_OP 宏前置 3 nop 双保险
- 2026-10-31 nop 税实验（exp02）：preload+unroll 结构下去 nop 三档优化
  均 36/36 通过，nop 开销恒为 756 cycle/次（1080 条指令中约 30% 被
  流水线停顿吸收）。当时结论是"软件保险冗余、但硬件缺口仍在，
  转入方案 B 修改 proc.v"——**该结论的前提同样错误**：
  preload+unroll 之所以"治好"，是因为它让 CFU 操作数不再包含
  变量 r，与指令间隔无关。

### 根因（2026-10-31，VCD 波形定位）
CFU_OP 宏是 GCC 语句表达式，内部声明了局部变量 `int r`。
当调用点写成 `CFU_MUL(img[r*8], kern[0])` 且外层循环变量也叫 `r` 时，
**宏内的 `int r` 遮蔽了循环变量**：操作数 `img[r*8]` 绑定到的是
宏内那个从未初始化的 `r`（分配到寄存器 a5），而非循环计数器。

波形证据（dump.vcd 分析）：
- 失败迭代的 CFU src1 = 0 或陈旧值；
- load 地址在正确的 0x100005ac 与野地址 0x1004ffac 之间振荡，
  野地址 = 数组基址 + (上一轮乘积 &lt;&lt; 5)——即上一轮 CFU 的结果
  被当作循环变量 r 去计算 img[r*8] 的偏移，自激振荡；
- 循环反汇编（PC 0x138-0x154）中没有任何对 a5 的逐轮初始化。

### 为什么加 nop 能"治好"
3 个 nop 改变了寄存器分配和指令排布，偶然让 a5 中的值变成无害值。
nop 从未修复任何硬件逻辑——它只是掩盖了软件 bug。

### 为什么多数实验免疫
conv/dot256 等正式实验中，CFU 操作数都是局部变量、字面量或
名为 i 的索引，没有任何与宏内 `r` 同名的变量，因此从不触发遮蔽。
T3/T4（先取出到临时变量再调宏）天然规避；P1–P5、L2/L3 探针
（无 r 表达式）全部通过，与根因完全吻合。

### 修复
宏内变量改名并去掉内置 nop：

    #define CFU_OP(f3, a, b) ({ \
        int _cfu_ret; \
        asm volatile(".insn r 0x0B, " #f3 ", 0, %0, %1, %2" \
            : "=r" (_cfu_ret) : "r" (a), "r" (b)); \
        _cfu_ret; \
    })

修复后 L1 探针在**零间隔**下输出全部正确（L1 = L3 =
10192 5096 0 -5096 -10192 7553）。硬件正式平反。

### 教训
1. GCC 对此 bug 保持沉默："=r" 输出约束使编译器认为变量已被写入，
   不触发未初始化诊断（实测 -Os 下无任何警告）。宏内临时变量必须
   采用不可能撞名的命名（如下划线前缀），不能指望编译器兜底。
2. "加 nop 就好了"不等于"硬件有 bug"——nop 改变寄存器分配，
   可能掩盖软件问题。应先隔离软件因素再怀疑硬件。
3. 波形分析（VCD）应更早使用；纯软件侧二分排查耗时约 3 周，
   波形定位只用了一个下午。

## #2 -O0 下内联汇编编译失败 — 已修复

- **现象**：`impossible constraint in 'asm'`
- **根因**：funct3 走 "i" 立即数约束，依赖编译器内联+常量传播，-O0 不内联
- **修复**：CFU_OP 改为宏字符串化（#f3 直接拼进指令文本），全优化级别兼容

## #3 程序映像固化导致"假结果" — 已知悉，流程规避

- **现象**：改 main.c 后 make run 结果不变
- **根因**：程序经 initf 生成 memi/memd.txt 后在 Verilate 时编进仿真器；
  make run 不触发重编译；且部分情况下 make（prog+build）后 Verilator
  仍判断"无变化"而跳过重建（2026-10-31 复现，子 make 报
  "Nothing to be done"）
- **规避**：改程序后 `rm -rf obj_dir && make && make run`，强制全新仿真器
