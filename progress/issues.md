## #1 custom-0 指令 load-use 冒险缺陷（上游框架）— 软件规避已证冗余，硬件修复进行中

- **状态**：in progress（方案 B / 任务① 实施中）
- **发现日期**：2026-10-06
- **现象**：conv3x3 CFU 版对拍 5/36，错误呈"行冻结"——第 0 行全对，
  其余每行结果精确等于第 0 行对应列
- **定位过程**：
  1. 排除除法假设（CFU 版消去除法仍失败；纯 C 版加除法仍正确）
  2. 探针 T1/T2（custom-0 直读刚加载的值）复现；E1（纯 C 对照）正常
  3. T3/T4 探针确认：lw 与 custom-0 之间隔 ≥1 条指令即正确
  4. 源码定位：proc.v 的 If_load_muldiv_use 对 load-use 仅停一拍，
     CFU 只被列入"生产者"一侧；lw 数据经同步 RAM 晚一拍返回，
     custom-0 作消费者紧跟 lw 时读到旧值
- **规避方案及其演化**：
  - 初版：预加载+展开结构 + CFU_OP 宏前置 3 nop 双保险；
  - 2026-10-31 nop 税实验证明：在预加载+展开结构下 3-nop 保险冗余，
    三档优化均无 nop 36/36 通过；nop 开销恒为 756 cycle/次
    （1080 条指令中约 30% 被流水线停顿吸收）。
    注意：冗余是该代码结构带来的经验结论，非硬件保证。
- **待办**：修改 proc.v hazard 逻辑将 custom-0 纳入 load-use 停顿（方案 B），
  使无 nop 正确性由硬件保证

## #3 程序映像固化导致"假结果" — 已知悉，流程规避

- **现象**：改 main.c 后结果不变
- **根因**：程序经 initf 生成 memi/memd.txt 后在 Verilate 时编进仿真器；
  make run 不触发重编译；且部分情况下 make（prog+build）后 Verilator
  仍判断"无变化"而跳过重建（2026-10-31 复现）
- **规避**：改程序后 `rm -rf obj_dir && make && make run`，强制全新仿真器
